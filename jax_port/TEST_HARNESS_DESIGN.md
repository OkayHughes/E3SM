# Test Harness Design — Validating JAX Ports Inside SCREAM/EAMxx

**Companion document:** [PORTING_PLAN.md](PORTING_PLAN.md) (what gets ported, in what order).
All paths relative to the E3SM repo root; `eamxx/` abbreviates `components/eamxx/`.

## 1. Goals and non-goals

- **Goal:** for each ported parameterization, demonstrate that the JAX implementation,
  swapped into EAMxx in place of the C++ one, reproduces SCREAM's behavior to within
  stated tolerances, using SCREAM's existing test machinery wherever possible.
- **Non-goal:** bit-for-bit equivalence. JAX reassociates floating-point operations
  (fusion, different transcendental implementations), so the acceptance criteria are
  tolerance-based (§7). EAMxx's BFB-only mechanisms (e.g. `bfbhash`) are used as *change
  detectors on the C++ side*, not as pass/fail for the port.
- **Constraint:** multiple contributors with different LLM tooling. Every tier below is
  runnable from a plain checkout with documented commands; golden data is generated by
  scripts checked into the repo, never hand-made.

## 2. The two existing Python bridges (both already in EAMxx)

EAMxx ships two mutually-exclusive Python integrations
(`eamxx/docs/user/python.md`); the harness uses both, for different tiers.

### Bridge A — "C++ calls Python": runtime swap of a process implementation
- Build flag `EAMXX_ENABLE_PYTHON` (CMake option at `eamxx/CMakeLists.txt:269`; defines
  `EAMXX_HAS_PYTHON`; links pybind11 embedded interpreter).
- Mechanism lives in the **base class**, so it is available to every process:
  - `eamxx/src/share/atm_process/atmosphere_process.cpp` (~lines 101–112): if the
    process's YAML has a non-empty `py_module_name`, the embedded interpreter starts
    (`eamxx/src/share/core/eamxx_pysession.hpp`), `py_module_path` is added to
    `sys.path`, and the module is imported.
  - Every registered field is exposed to Python as a zero-copy `pybind11::array`
    aliasing the field buffer, with strides that account for pack padding
    (`eamxx/src/share/field/field_pyutils.hpp`; accessors `get_py_field_host/dev` and
    `py_module_call(...)` in `atmosphere_process_pyhelpers.hpp`).
  - The process's `run_impl` chooses at runtime:
    `if (has_py_module()) { sync_to_host; py_module_call("main", args...); sync_to_dev; return; }`
    else run the native C++. Reference implementation:
    `eamxx/src/physics/cld_fraction/eamxx_cld_fraction_process_interface.cpp`
    (lines ~74–150), with Python modules `cld_fraction_numpy.py` / `cld_fraction_cupy.py`
    in the same directory. YAML keys: `py_module_name`, `py_module_path`,
    `py_backend` (`host`|`device`).
- **This is the production harness path**: the JAX port runs *inside* a real EAMxx run,
  and everything downstream (output streams, cprnc comparisons, multi-process tests,
  CIME cases) works unchanged.

### Bridge B — "Python drives EAMxx": pyeamxx single-process driver
- Build flag `EAMXX_ENABLE_PYSCREAM` (`eamxx/src/CMakeLists.txt:16–19`); nanobind module
  `pyeamxx_ext` under `eamxx/src/python/` (package `pyeamxx`).
- Exposes `init/finalize`, `create_grids_manager(ncols, nlevs, ic_file)`, and
  `AtmProc(params, name)` with `read_ic`, `initialize(t0)`, `run(dt)`,
  `get_field(name)` (numpy view sharing the host buffer), `setup_output(yaml)`.
  Canonical example: `eamxx/tests/python/pyp3/p3_standalone.py`, with a CMake test that
  runs the same config through the C++ AD and cprnc-compares
  (`eamxx/tests/python/pyp3/CMakeLists.txt`).
- **This is the golden-data factory and interactive debugger**: from one Python script
  you can snapshot every input field before a `run(dt)` and every output after it
  (`np.save`), then feed those arrays to the JAX implementation in pytest — no C++
  rebuild in the inner loop.

## 3. The adapter contract (one pattern for every process)

Each ported package keeps its numerics pure and hangs an EAMxx-facing shim off the side:

```
jax_port/scream_jax/<pkg>/           # pure JAX: state-in → state-out, jit-able
jax_port/scream_jax/adapters/eamxx/<pkg>_eamxx.py
```

The adapter module is what `py_module_name` points at. It must expose exactly what the
process's `run_impl` calls (matching `cld_fraction_numpy.py`'s shape):

```python
def init():                       # called from initialize_impl
    ...  # load tables, build jitted fn, enable x64

def main(<scalars...>, <in/out numpy arrays in the exact order the C++ passes them>):
    # 1. wrap inputs:   jnp.asarray(x)  (host backend: arrays are numpy views)
    # 2. call the pure jitted kernel
    # 3. write back IN PLACE:  out_np[...] = np.asarray(result)
```

Rules:
- `jax.config.update("jax_enable_x64", True)` unconditionally in `init()`.
- Adapters never contain physics; pure code never does in-place writes.
- Argument order is part of the C++ change for each process (§4) and is documented in
  the adapter docstring — it is the single most fragile joint in the harness.
- Start with `py_backend: host` everywhere (numpy views + explicit syncs). A
  `device` path via dlpack/CuPy interop is a later optimization, not needed for
  validation.

## 4. Per-process C++ enablement work

Only `cld_fraction` (and the ML variant `cld_frac_net`) currently branch on
`has_py_module()`. For each other ported process a small, mechanical C++ patch is
needed in its `eamxx_<pkg>_process_interface.cpp`:

1. In `initialize_impl`: `if (has_py_module()) py_module_call("init");`
2. In `run_impl`, before the native call: gather `get_py_field_host(...)` for every
   required/updated/computed field, `py_module_call("main", dt, <runtime scalars>,
   <arrays>)`, sync, `return`.
3. Guard with `#ifdef EAMXX_HAS_PYTHON` (match the cld_fraction pattern).

Decision to respect when writing these patches: **place the Python call at the same
point as the C++ kernel call, i.e. *after* the interface's pre-process loop and
*before* its post-process loop** (wet→dry conversions, θl construction, etc. stay in
C++). This keeps the swapped unit identical to the unit tested by the kernel tests, and
the pre/post conversions get ported and validated separately as part of the pySEs
assembly layer (they're in `scream_jax` too, just validated at Tier 0/3 rather than by
the swap test). Exception: where the pre/post loop is trivial, swapping the whole
`run_impl` is acceptable — record the choice in the adapter docstring.

Estimated patch size: ~50–100 lines per process; P3 and SHOC pass ~30–40 arrays, RRTMGP
more (consider passing a dict/kwargs via pybind if the positional list gets unwieldy).

## 5. Validation tiers

### Tier 0 — pure-Python kernel tests (pytest, no EAMxx build)
- **Golden data source:** Bridge B scripts (per package,
  `jax_port/harness/gen_golden_<pkg>.py`) that run the C++ process (or, for
  sub-kernels, the C++ `*_run_and_cmp` / unit-test executables' stored baseline files)
  and dump `.npz` input/output pairs. Two complementary generators:
  1. *Whole-scheme*: pyeamxx `AtmProc` — snapshot all fields before/after `run(dt)`
     across N timesteps and M columns of the standard 218-column/72-level IC file
     (`EAMxx_tests_IC_FILE_72lev`).
  2. *Per-kernel*: the existing baseline machinery. P3/SHOC per-kernel tests
     (`eamxx/src/physics/{p3,shoc}/tests/`) already serialize every kernel's exact
     argument list via `PhysicsTestData`
     (`eamxx/src/share/physics/physics_test_data.*`,
     `physics_test_read_write_helpers.hpp`) into `${SCREAM_BASELINES_DIR}/data` when run
     with `-g`. A small one-time Python reader for that binary format (or a C++ dumper
     patch that re-emits as `.npz`) turns the *entire existing per-kernel test suite*
     into golden data for the port. The per-kernel `*Data` structs in
     `tests/infra/{p3,shoc}_test_data.hpp` are the authoritative argument-list spec.
- **Checks:** `np.testing.assert_allclose` with per-kernel tolerances (§7), plus ports
  of each kernel's `run_property()` invariants (monotonicity, bounds, conservation) —
  these catch logic errors tolerances can't.
- Runs anywhere (CI, laptops), pure pip environment: `jax, numpy, netCDF4, pytest`.

### Tier 1 — whole-scheme comparison in Python (pytest + pyeamxx)
- Same script pattern as the pyp3 example: drive the C++ process via `AtmProc.run(dt)`
  and the JAX `<pkg>_main` side-by-side from identical ICs for O(10–100) steps;
  compare trajectories field-by-field with tolerance growth tracking (§7).
- This is the fast inner loop while assembling `p3_main`/`shoc_main` from validated
  kernels, and it needs the EAMxx build only once (`EAMXX_ENABLE_PYSCREAM=ON`).

### Tier 2 — in-situ single-process swap (the headline validation)
- Template: `eamxx/tests/single-process/cld_fraction/CMakeLists.txt`, which already
  runs the same AD standalone test three ways (cpp / numpy / cupy) and compares NetCDF
  outputs pairwise.
- For each process, add to its `eamxx/tests/single-process/<pkg>/` directory:
  - `input_jax.yaml` — copy of `input.yaml` plus
    `py_module_name: <pkg>_eamxx`, `py_module_path: <repo>/jax_port/scream_jax/adapters/eamxx`,
    `py_backend: host` (CMake `configure_file` variables, matching the cld_fraction
    pattern).
  - A CMake block (guarded by `EAMXX_ENABLE_PYTHON`) that runs the standalone exe with
    the JAX yaml and compares against the C++ run using
    `eamxx/scripts/compare-nc-files --tol <tol>` (tolerance-capable; use it instead of
    the BFB `CprncTest.cmake` used for cpp-vs-cupy).
  - Output stream configured `averaging_type: instant`, `frequency: 1 nsteps` so every
    step is compared, over the standard short run (matches existing tests' step counts).
- TMS has no single-process test today — either add one (mirroring shoc's) or accept
  Tier-0/1 coverage plus its appearance in Tier 3; RRTMGP additionally reuses the
  existing allsky reference comparison
  (`eamxx/src/physics/rrtmgp/tests/rrtmgp_tests.cpp` semantics) as a Tier-0 golden set.
- **Run commands** (no HPC needed — the agent/dev environment works on a laptop/CI box):
  ```bash
  source components/eamxx/scripts/setup-copilot-env.sh     # TPLs, submodules, data
  cd components/eamxx
  ./scripts/test-all-eamxx -m copilot-testing -t dbg --config-only \
      # then add: -DEAMXX_ENABLE_PYTHON=ON (and/or EAMXX_ENABLE_PYSCREAM=ON)
  cd ctest-build/copilot-testing/full_debug && make -j && ctest -R <pkg>_standalone
  ```
  (On supported HPC machines, the same via `test-all-eamxx -m <machine>`; in CIME cases,
  `./xmlchange --append SCREAM_CMAKE_OPTIONS='EAMXX_ENABLE_PYTHON ON'` — see
  `eamxx/docs/developer/torch_support.md`.)

### Tier 3 — multi-process and full-model
1. **Physics-only coupled test:** `eamxx/tests/multi-process/physics_only/
   shoc_cld_spa_p3_rrtmgp/` with one process at a time swapped to JAX, then cumulatively
   (shoc+cld+p3, finally +rrtmgp). Comparison as in Tier 2. This is where inter-process
   field-contract errors surface.
2. **Dynamics+physics standalone:** `eamxx/tests/multi-process/dynamics_physics/
   homme_shoc_cld_spa_p3_rrtmgp[_pg2]/` — validates the swap under a real dycore,
   subcycling, and pg2 remap (tms included).
3. **CIME case:** `F2010-SCREAMv1` at `ne4pg2_ne4pg2` (per repo AGENTS.md) with
   `SCREAM_CMAKE_OPTIONS` enabling Python; run SMS_Ln5-style smoke plus a multi-day run
   for the climate-statistics check (§7.3). CIME suites for regression context:
   `e3sm_eamxx_v1_lowres` etc. in `cime_config/tests.py`.
4. **C++-side no-regression guard:** with `py_module_name` unset, the patched build must
   remain BFB with baseline (`test-all-eamxx -b`, `--eamxx-bfbhash` testmod) — proving
   the enablement patches (§4) are inert when Python is off.

## 6. Determinism hazards (must be neutralized for comparison runs)

| Hazard | Where | Mitigation in harness runs |
|---|---|---|
| MCICA random subcolumn sampling | `get_subsampled_clouds` in `eamxx/src/physics/rrtmgp/eamxx_rrtmgp_interface.hpp` | Port the same seeded generator (seed derives from column/state), or compare clear-sky + fixed-cloud configurations first; document the RNG contract in the rrtmgp adapter |
| Radiation cadence | `rad_frequency` | Set to 1 in comparison yamls |
| Subcycling | `mac_aero_mic` `number_of_subcycles` | Keep the test defaults; Python must implement identical subcycle dt |
| Adaptive sedimentation substeps (P3) | `p3_*_sed` kernels | Substep count is state-dependent; port the same substep logic, compare per-step at Tier 0 before whole-scheme |
| Saturation-function branch | `Polysvp1` vs `MurphyKoop` | Match the runtime option from input.yaml |
| Precision | build type | Compare against `dbg`/double builds only (`SCREAM_DOUBLE_PRECISION`); JAX x64 |

## 7. Acceptance criteria

### 7.1 Kernel level (Tier 0)
Relative error `rtol ≤ 1e-12`–`1e-10` (double precision, same algorithm, different
op ordering) for algebraic kernels; looser (`1e-8`) where transcendentals/iterative
loops dominate (saturation adjustment, PDF inversion, table interpolation). Each kernel
records its tolerance and justification in the test.

### 7.2 Single-process trajectory (Tiers 1–2)
Per-field relative L2 and L∞ errors at each output step must stay below a per-package
envelope (starting point: `1e-8` at step 1, growth documented over the run; the
cld_frac_net precedent uses `--tol 1e-6` for an ML emulator — a numerics port should do
much better). Failures analyzed field-first: the field with the earliest divergence
localizes the defective kernel.

### 7.3 Coupled/full-model (Tier 3)
Trajectories diverge chaotically; use short runs (≤ a few days) for envelope checks and
rely on ensemble-style climate statistics for longer runs (mean/variance of standard
fields vs the C++ run — reuse the output presets from the eamxx testmods). A formal
MVK/PGN-style statistical test is a stretch goal; initial acceptance is expert review of
difference maps plus the short-run envelopes.

## 8. Repository layout for harness assets

```
jax_port/
  PORTING_PLAN.md, TEST_HARNESS_DESIGN.md      (these documents)
  scream_jax/                                   (the package — see plan §8)
    foundation/  shoc/  p3/  cld_fraction/  tms/  spa/  rrtmgp/
    adapters/eamxx/                             (py_module_name targets)
  harness/
    gen_golden_<pkg>.py                         (Bridge-B golden-data generators)
    baselines_reader.py                         (PhysicsTestData binary → npz)
    compare_trajectories.py                     (tolerance-envelope checker)
  tests/                                        (pytest: Tier 0/1)
```

C++-side changes stay in-tree next to the code they touch (process-interface patches,
`input_jax.yaml` + CMake blocks under `eamxx/tests/single-process/<pkg>/`), so the diff
against upstream E3SM remains reviewable per package.

## 9. Milestone sequence (matches the porting order)

1. **M0 — toolchain proof:** `cld_fraction_jax.py` passing the existing single-process
   cpp-vs-py comparison (Tier 2). Deliverables: build recipe with
   `EAMXX_ENABLE_PYTHON=ON` verified, adapter pattern established.
2. **M1 — golden-data factory:** pyeamxx build verified; `gen_golden_p3.py` /
   `gen_golden_shoc.py` producing npz sets; baseline-reader for per-kernel data.
3. **M2 — tms + foundation** validated at Tier 0 (+Tier 2 if a tms standalone test is
   added).
4. **M3 — shoc** through Tiers 0→2; **M4 — p3** likewise (parallelizable with M3).
5. **M5 — spa** (Tier 2) and **M6 — rrtmgp** (Tier 0 allsky reference → Tier 2).
6. **M7 — coupled:** shoc_cld_spa_p3_rrtmgp all-JAX (Tier 3.1), then homme-coupled and
   the F2010-SCREAMv1 CIME case (Tier 3.2–3.3).
7. Throughout: Tier 3.4 no-regression guard on every C++ enablement patch.
